ShortX 自动指令使用教程

1. 简介

ShortX 是一个功能强大的 Android 自动化工具，同时作为标准 Android 应用和 Xposed/Magisk 模块运行。它允许用户通过配置"自动指令"和"一键指令"来自动化手机上的各种操作。

核心能力：
- 监听系统事件（通知、应用切换、按键、传感器等）
- 基于条件判断执行自动化操作
- 支持 Shell 命令、JavaScript、MVEL 脚本
- 浮窗、侧边栏、状态栏芯片等 UI 交互
- 手势录制与回放
- OCR 文字识别
- WebSocket 通信
- WebDAV 备份同步

2. 安装与环境要求

基本要求：
- Android 系统
- Root 权限（部分功能需要）
- Xposed/LSPosed 框架（Xposed 相关功能需要）

安装方式：
- 作为普通 Android 应用安装 APK
- 作为 Magisk/Zygisk 模块安装

首次使用：
1. 安装后打开应用
2. 授予必要的权限（无障碍服务、通知监听等）
3. 如果使用 Xposed 功能，确保在 LSPosed 中激活模块
4. 开始创建自动指令或导入社区指令

3. 核心概念

ShortX 的自动化基于三个核心概念：触发器 → 条件 → 动作。

3.1 自动指令 (Rule)

自动指令是自动化的主体。当指定的触发器事件发生时，系统会检查条件是否满足，如果满足则执行动作。

自动指令结构：

触发器 (Facts)  →  条件 (Conditions)  →  动作 (Actions)
     ↓                  ↓                    ↓
  事件监听          前置判断             实际执行

自动指令属性：

属性说明
facts触发器列表，定义何时触发自动指令
conditions条件列表，定义触发后是否执行
actions动作列表，定义触发后执行什么
isEnabled自动指令是否启用
condOp条件组合方式（ALL/ANY/NONE/MVEL）
asyncMode异步模式（Async/Sync/Sync_InRule）
conflictPolicy冲突策略（ExecuteBoth/ReplaceOld/SkipNew）
hook钩子，自动指令启用/禁用/删除时执行的动作
quit退出指令，满足条件时停止自动指令执行
parameters指令参数，可在导入时自定义
ruleInstanceIdGenerator指令实例 ID 生成器（见下方详解）

condOp 条件组合方式

控制多个条件之间的逻辑关系。对应代码 ConditionEvaluatorImpl.kt 中的 when (condOp) 分支。

值逻辑说明
ALLAND所有条件都满足时才执行（默认）
ANYOR任一条件满足即执行
NONENOR所有条件都不满足时才执行
MVEL自定义用 MVEL 表达式自定义条件组合逻辑

ALL（默认）：需要同时满足多个条件

条件1: 当前应用是微信
条件2: 屏幕是亮的
条件3: WiFi 已连接
→ 三个条件全部满足才执行动作

ANY：满足任一条件即可

条件1: 当前应用是微信
条件2: 当前应用是 QQ
→ 只要在微信或 QQ 中就执行动作

NONE：所有条件都不满足才执行

条件1: 在通话中
条件2: 屏幕是息屏的
→ 既不在通话中，屏幕也不是息屏状态才执行

MVEL：需要复杂的条件组合逻辑时使用。在表达式中用 c1、c2、c3... 引用各条件的评估结果（c1.call() 执行第 1 个条件）。

// 条件1 AND (条件2 OR 条件3)
c1.call() && (c2.call() || c3.call())

// 条件1 为真，但条件2 和 条件3 不同时为真
c1.call() && !(c2.call() && c3.call())

asyncMode 多指令同异步策略

控制多个自动指令之间的执行关系。对应代码 DefaultRuleEngine.kt 中 runActionsJobLocked 方法的 when (asyncMode) 分支。

值说明锁机制
Async异步执行，不同指令的动作并行执行无锁
Sync同步执行，不同指令的动作按先后顺序依次执行全局互斥锁 globalMuteX
Sync_InRule同指令同步，相同指令按顺序执行，不同指令之间仍然并行指令级互斥锁 muteX

Proto 定义：

{
  "asyncMode": "AsyncMode_Async",
  "actionAsyncMode": "ActionAsyncMode_Sync"
}

Async（默认）：各指令独立执行，互不影响

自动指令A: 收到通知 → 弹幕显示（耗时 2 秒）
自动指令B: 收到通知 → 发送 HTTP 请求（耗时 3 秒）
→ A 和 B 同时开始，各自独立完成

Sync：严格按顺序执行，避免并发冲突

自动指令A: 充电插拔 → 执行 Shell 命令修改充电参数
自动指令B: 充电插拔 → 执行另一个 Shell 命令
→ A 先执行完，B 再执行，避免 Shell 命令冲突

⚠️ 注意：Sync 模式使用全局锁，不要在同步指令内执行耗时动作（特别长的延迟、死循环），否则会阻塞其他指令。

Sync_InRule：同一指令串行，不同指令并行

自动指令A: 通知触发 → 执行动作序列（2秒）
自动指令A: 再次通知触发 → 等待上一次执行完再执行
自动指令B: 通知触发 → 不受影响，立即执行

与 actionAsyncMode 的区别：

  • asyncMode：控制指令之间的执行关系
  • actionAsyncMode：控制同一指令内各动作之间的执行关系（Sync 顺序执行 / Async 并行执行）

conflictPolicy 冲突策略

当同一自动指令的触发器连续触发、且上一次执行尚未完成时的处理策略。对应代码 DefaultRuleEngine.kt 中 Check ConflictStrategy 段落。

值说明
ExecuteBoth同时执行新旧任务（默认）
ReplaceOld取消旧任务，执行新任务
SkipNew跳过新任务，保留旧任务

ExecuteBoth（默认）：适合互不影响的操作

触发器: 收到通知
动作: 弹幕显示通知内容
→ 第一条通知还在弹幕中，第二条来了也同时弹幕

ReplaceOld：适合状态更新类操作，只关心最新状态

{"@type": "type.googleapis.com/WiFi"} 信号强度变化
动作: 更新状态栏 Chip 显示当前信号强度
→ 新信号来了，旧的显示过时了，应该取消旧的并更新为新的

SkipNew：适合防重复操作

触发器: 连接蓝牙
动作: 自动播放音乐
→ 第一次连接蓝牙开始播放了，短时间内再次触发不重复播放

判断逻辑（代码）：

// DefaultRuleEngine.kt 第 270-297 行
if (isThisRuleAlreadyRunning) {
    shouldExecuteActions = when (conflictStrategy) {
        ExecuteBoth -> true           // 允许新任务
        ReplaceOld -> {
            cancelJobs(...)           // 取消旧任务
            true                      // 允许新任务
        }
        SkipNew -> false              // 拒绝新任务
    }
}

quit 退出指令

当触发器事件不匹配自动指令的正常触发器时，系统会检查退出逻辑。如果退出触发器匹配且退出条件满足，则取消该指令正在运行的任务，并执行退出动作。

退出流程（代码 DefaultRuleEngine.kt 第 389-484 行）：

正常触发器不匹配
  → 检查 quit.isEnabled
  → 检查退出评估策略 (evaluatePolicy)
  → 匹配退出触发器 (quit.facts)
  → 评估退出条件 (quit.conditions)
  → 取消运行中的任务 (cancelJobs)
  → 执行退出动作 (quit.actions)

退出评估策略 (Quit_EvaluatePolicy)：

策略说明代码逻辑
Always总是评估退出逻辑每次触发器事件都检查
Only_When_Is_Running仅当有运行中的任务时评估activeJobs() 包含该指令才检查
Once每次执行指令后仅评估一次quitEvaPolicyOO 集合记录已评估的指令

{

    "@type": "type.googleapis.com/RuleInstanceIdGenerator_Static",
    "insId": "固定实例ID"
  }
}

String Proto：

{
  "ruleInstanceIdGenerator": {
    "@type": "type.googleapis.com/RuleInstanceIdGenerator_String",
    "insId": "{pkgName}"
  }
}

MVEL Proto：

{
  "ruleInstanceIdGenerator": {
    "@type": "type.googleapis.com/RuleInstanceIdGenerator_MVEL",
    "expression": ""group_" + ({batteryLevel} > 50 ? "high" : "low")"
  }
}

JS Proto：

{
  "ruleInstanceIdGenerator": {
    "@type": "type.googleapis.com/RuleInstanceIdGenerator_JS",

Static（默认）：同一指令只保留一个任务

3.2 一键指令 (Direct Action)

一键指令是无需触发条件、手动执行的动作序列。

与自动指令的区别：
- 没有触发器（Facts）
- 用户手动点击执行
- 适合快捷操作（如蓝牙开关、WiFi开关）

一键指令结构：

动作 1 → 动作 2 → 动作 3 → ...

一键指令属性：

属性说明
actions动作列表
hook钩子，启动/停止时执行的动作
quit退出机制
| parameters

3.3 事实/触发器 (Fact)

触发器定义了"什么时候"触发自动指令。每个 Fact 对应一类系统事件。

所有 Fact 都有的字段：

字段说明
tag标签，用于在条件中通过 RequireFactTag 判断是哪个触发器触发的
customContextDataKey自定义上下文数据映射
id唯一标识
isDisabled是否禁用
| note

示例：AppBecomeFg（应用进入前台）

{
  "@type": "type.googleapis.com/AppBecomeFg",
  "apps": [{"pkgName": "com.tencent.mm"}],
  "tag": "微信前台",
  "id": "F-xxx"
}

3.4 条件 (Condition)

条件定义了"满足什么要求"才执行动作。

所有 Condition 都有的字段：

4.1 全局变量 (Global Variable)

全局变量是永久保存的数据盒子，存放在手机本地。你创建了它，它就一直在那里，直到你手动删除。不同的自动指令之间可以通过全局变量共享数据。

通俗理解： 全局变量就像手机上的"备忘录"，你在一条自动指令里写入了一段文字，另一条自动指令也能读到。

变量类型

全局变量有 6 种类型，分别装不同种类的数据：

类型能装什么通俗解释举例
StringVar文字一个文字盒子"Hello"、"com.tencent.mm"、"12345"
Int64Var数字一个数字盒子0、1、100、-5
BoolVar真/假一个开关盒子（开/关）true（开）、false（关）
StringListVar文字列表一个文字盒子的货架["苹果", "香蕉", "橘子"]
Int64ListVar数字列表一个数字盒子的货架[1, 2, 3, 100]
BoolListVar开关列表一个开关盒子的货架[true, false, true]

创建全局变量

使用 CreateGlobalVar 动作创建一个全局变量。对应代码 CreateGlobalVar.kt。

示例：创建一个"WiFi状态"变量

{
  "@type": "type.googleapis.com/CreateGlobalVar",
  "globalVar": {
    "name": "WiFi状态",
    "type": {"@type": "type.googleapis.com/StringVar"}
  }
}

这条指令会在系统中创建一个叫"WiFi状态"的字符串变量，初始值为空。之后你就可以往里面写入数据了。

实际场景： 你创建一个"蓝牙连接次数"变量来统计蓝牙连接了多少次。

{
  "@type": "type.googleapis.com/CreateGlobalVar",
  "globalVar": {
    "name": "蓝牙连接次数",
    "type": {"@type": "type.googleapis.com/Int64Var"}
  }
}

写入全局变量

使用 WriteGlobalVar 动作往变量里写入数据。对应代码 WriteGlobalVar.kt。

最简单的用法——直接写入值：

{
  "@type": "type.googleapis.com/WriteGlobalVar",
  "varName": "WiFi状态",
  "valueAsString": "已连接",
  "op": "WriteGlobalVarOp_Override"
}

这条指令把"WiFi状态"变量的值设为"已连接"。Override 表示直接覆盖，不管之前是什么。

写入操作详解

WriteGlobalVar 支持 15 种写入方式，对应代码 WriteGlobalVar.kt 中的 handleGVOp 方法：

操作通俗解释举例（假设变量原值为 "AB"）
Override直接覆盖，不管之前是什么"AB" → 写入 "CD" → 变成 "CD"
AppendToLast在末尾追加"AB" → 追加 "CD" → 变成 "ABCD"
AppendToFirst在开头插入"AB" → 插入 "CD" → 变成 "CDAB"
DeleteValue删除指定内容"ABCD" → 删除 "BC" → 变成 "AD"
DeleteLast删除列表最后一个列表 [A,B,C] → 变成 [A,B]
DeleteFirst删除列表第一个列表 [A,B,C] → 变成 [B,C]
RemoveAtIndex删除列表指定位置列表 [A,B,C] → 删除第1个 → 变成 [A,C]
Clear清空所有内容列表 [A,B,C] → 变成 []
Reverse反转列表顺序列表 [A,B,C] → 变成 [C,B,A]
Shuffle随机打乱列表列表 [A,B,C] → 变成 [B,A,C]（随机）
Plus1数字加 15 → 变成 6
Minus1数字减 15 → 变成 4
Invert布尔取反（开→关，关→开）true → 变成 false
PlusDelta数字加指定值5 → 加 10 → 变成 15
MinusDelta数字减指定值5 → 减 3 → 变成 2

实际场景 1：统计蓝牙连接次数

每次蓝牙连接时，把"蓝牙连接次数"加 1：

{
  "@type": "type.googleapis.com/WriteGlobalVar",
  "varName": "蓝牙连接次数",
  "valueAsString": "1",
  "op": "WriteGlobalVarOp_PlusDelta"
}

实际场景 2：记录最近连接的蓝牙设备

用一个列表变量保存最近 3 个连接过的蓝牙设备：

{
  "@type": "type.googleapis.com/WriteGlobalVar",
  "varName": "最近蓝牙设备",
  "valueAsString": "小米耳机",
  "op": "WriteGlobalVarOp_AppendToLast"
}

每次新连接追加到末尾，如果列表太长，可以再用 DeleteFirst 删除最早的记录。

实际场景 3：WiFi 开关状态记忆

用一个布尔变量记住 WiFi 当前状态（开/关），用来做切换：

// 第一步：读取当前状态，判断是开还是关
// 如果是关 → 开启 WiFi → 把变量设为 true
// 如果是开 → 关闭 WiFi → 把变量设为 false

{
  "@type": "type.googleapis.com/WriteGlobalVar",
  "varName": "WiFi开关状态",
  "valueAsString": "true",
  "op": "WriteGlobalVarOp_Invert"
}

删除全局变量

使用 DeleteGlobalVar 动作删除不再需要的变量。

{
  "@type": "type.googleapis.com/DeleteGlobalVar",
  "varName": "蓝牙连接次数"
}

建议： 在自动指令的"被删除时"钩子中清理不再使用的全局变量，保持整洁。

向列表变量添加元素

使用 AddToGlobalVar 动作向列表变量追加一个新元素：

{
  "@type": "type.googleapis.com/AddToGlobalVar",
  "varName": "最近蓝牙设备",
  "valueAsString": "蓝牙音箱"
}

跨指令共享数据

全局变量最大的优势是跨指令共享。比如：

  • 指令 A 监听 WiFi 连接，把当前 WiFi 名称写入全局变量 "当前WiFi"
  • 指令 B 在其他时机读取"当前WiFi"变量，判断是否在家

这两条指令不需要直接通信，通过全局变量就能传递信息。

4.2 局部变量 (Local Variable)

局部变量是临时的数据盒子，只在当前这条指令执行期间有效。指令执行结束后，局部变量就会被自动销毁。

通俗理解： 局部变量就像你在纸上写的临时笔记——事情办完了，纸就扔了。它不会影响其他指令，也不会被其他指令看到。

为什么要用局部变量？

  • 避免污染：不想让临时数据占用全局变量的位置
  • 安全性：临时数据不会被其他指令意外修改
  • 性能：不需要持久化保存的数据用局部变量更合适

创建局部变量

使用 CreateLocalVar 动作创建局部变量。对应代码 CreateLocalVar.kt。

{
  "@type": "type.googleapis.com/CreateLocalVar",
  "localVar": {
    "name": "临时搜索结果",
    "type": {"@type": "type.googleapis.com/StringVar"}
  }
}

写入局部变量

使用 WriteLocalVar 动作写入局部变量：

{
  "@type": "type.googleapis.com/WriteLocalVar",
  "varName": "临时搜索结果",
  "valueAsString": "找到 3 条匹配记录"
}

局部变量的实际场景

场景：剪贴板搜索

搜索剪贴板内容时，需要一个临时变量来存储搜索结果，搜索完显示给用户就行了，不需要永久保存：

// 步骤1：创建局部变量
{
  "@type": "type.googleapis.com/CreateLocalVar",
  "localVar": {"name": "搜索结果", "type": {"@type": "type.googleapis.com/StringVar"}}
}

// 步骤2：执行搜索，结果自动存入 {shellOut}
{"@type": "type.googleapis.com/ShellCommand", "command": "grep '关键词' /path/to/clipboard.txt"}

// 步骤3：把搜索结果写入局部变量
{
  "@type": "type.googleapis.com/WriteLocalVar",
  "varName": "搜索结果",
  "valueAsString": "{shellOut}"
}

// 步骤4：用对话框显示搜索结果
{
  "@type": "type.googleapis.com/ShowAlertDialog",
  "title": "搜索结果",
  "message": "{搜索结果}"
}

// 指令执行结束后，"搜索结果"变量自动销毁

4.3 上下文变量 (Context Variable)

上下文变量是系统自动填充的运行时数据，你不能手动创建或修改，只能读取使用。

通俗理解： 上下文变量就像系统递给你的"快递单"——上面写着包裹的来源、内容、时间等信息，你只需要看一眼就能用，不需要自己填写。

核心特点：

  • 自动填充：系统根据当前事件自动填入数据
  • 只读：你不能修改它的值
  • 临时有效：只在当前动作执行期间存在
  • 用花括号引用：{变量名}

常见上下文变量

自定义上下文变量名 (customContextDataKey)

几乎所有的触发器和动作都有一个 customContextDataKey 字段，允许你重命名输出的上下文变量。对应代码 CustomContextDataKey.kt。

通俗理解： 系统默认用固定的变量名（如 {shellOut}），但你可以给它取一个更有意义的名字（如 {命令结果}），这样在后续动作中更容易理解。

原理： 每个动作执行后，会调用 customContextDataKey.forKey(原始变量名) 检查是否有自定义映射。如果有，就用自定义名；如果没有，就用原始名。

配置方式： 在动作的 JSON 中添加 customContextDataKey 字段：

{
  "@type": "type.googleapis.com/ShellCommand",
  "command": "dumpsys battery | grep level",
  "customContextDataKey": {
    "keys": [
      {"first": "shellOut", "second": "电量原始数据"}
    ]
  }
}
// 原本输出到 {shellOut}，现在输出到 {电量原始数据}

实际场景：

在同一条指令中多次执行 ShellCommand 时，每次输出都会覆盖 {shellOut}。通过自定义变量名，可以让每次输出存到不同的变量中：

// 第一次：获取电量
{
  "@type": "type.googleapis.com/ShellCommand",
  "command": "dumpsys battery | grep level",
  "customContextDataKey": {"keys": [{"first": "shellOut", "second": "电量数据"}]}
}
// 输出到 {电量数据}

// 第二次：获取温度
{
  "@type": "type.googleapis.com/ShellCommand",
  "command": "dumpsys battery | grep temperature",
  "customContextDataKey": {"keys": [{"first": "shellOut", "second": "温度数据"}]}
}
// 输出到 {温度数据}

// 两个变量互不干扰，可以同时使用
{"@type": "type.googleapis.com/ShowToast", "message": "电量: {电量数据}, 温度: {温度数据}"}

函数返回值写入上下文变量

函数（Function）可以通过 resultContextDataKey 字段指定返回值写入的上下文变量名。对应代码 Functions.proto 中的 Function.resultContextDataKey。

配置方式：

{
  "@type": "type.googleapis.com/ExecuteFunction",
  "functionId": "get-weather",
  "resultContextDataKey": "天气结果"
}
// 函数执行后，返回值会写入 {天气结果}

如果留空，返回值不会写入任何上下文变量（但仍然可以通过 SetFunctionReturnValue 在函数内部设置返回值）。

5触发器 (Fact) 完整参考

触发器定义了什么时候触发自动指令。每个触发器对应一类系统事件，当事件发生时，系统会检查是否有匹配的自动指令。

5.1 应用生命周期

AppBecomeFg — 应用进入前台

当一个应用从后台切换到前台（成为屏幕顶部可见应用）时触发。

上下文变量：

变量名说明
{"pkgName"}应用包名
{"userId"}用户 ID
{"appLabel"}应用名称

HttpRequest — HTTP 请求

发送 HTTP 请求并处理响应。支持自定义 URL、方法、请求头、请求体、Cookie 持久化、SSL 信任，以及响应内容自定义解析为上下文变量。对应代码 HttpRequest.kt。

Proto 定义：

{
  "@type": "type.googleapis.com/HttpRequest",
  "url": "示例值",
  "method": "GET",
  "headers": [{"key": "Content-Type", "value": "application/json"}],
  "withCookieJar": false,
  "trustAllCerts": false,
  "executeInAppProcess": false
}

参数详解

参数类型说明
url字符串请求 URL，支持变量插值（如 globalVarOf$apiUrl）
method枚举请求方法：GET / POST / PUT / PATCH / DELETE / HEAD
headers列表请求头列表，每项包含 key 和 value，支持变量插值
requestBodyAny请求体，支持三种类型（见下方）
adapterAny响应解析适配器，决定如何解析响应并输出上下文变量（见下方详解）
withCookieJar布尔是否启用 Cookie 持久化（自动保存/发送 Cookie）
trustAllCerts布尔是否信任所有 SSL 证书（跳过证书验证）
executeInAppProcess布尔是否在应用进程中执行（默认在 system_server 中执行）

请求体类型 (requestBody)

类型说明字段
HttpRequestBodyJsonJSON 请求体json（JSON 字符串，支持变量插值）
HttpRequestBodyForm表单请求体items（键值对列表）
（不设置）无请求体适用于 GET/HEAD 请求

响应解析适配器 (adapter) — 核心功能

适配器决定了 HTTP 响应如何被解析，以及输出哪些上下文变量。对应代码 HttpRequest.kt 中的 handleResponseBody 方法。

适配器类型说明输出变量
HttpRequestRawAdapter原始适配器（默认）：直接返回响应体原文{httpRequestRet}（响应体字符串）
HttpRequestJsonMapAdapterJSON 解析适配器：用 MVEL 表达式从 JSON 响应中提取字段{httpRequestRet1}、{httpRequestRet2}...（每个表达式一个变量）
HttpRequestHeaderBodyJsonMapAdapterHeader+Body 解析适配器：同时解析响应头和 JSON 响应体{httpRequestRet1}、{httpRequestRet2}...（可访问 headers 和 body）

HttpRequestJsonMapAdapter 详解

当响应是 JSON 格式时，可以用 MVEL 表达式从 JSON 中提取任意字段。每个表达式的结果会存入对应的上下文变量。

原理（代码第 180-203 行）：

  1. 将响应体解析为 JSON 对象
  2. 对每个 expression 执行 MVEL 表达式，JSON 对象作为变量传入
  3. 每个表达式的结果存入 {httpRequestRetN}（N 从 1 开始）

示例：解析天气 API 响应

// 响应 JSON: {"temperature": 25, "humidity": 60, "city": "北京"}
// 配置 adapter:
{
  "@type": "type.googleapis.com/HttpRequestJsonMapAdapter",
  "expressions": ["temperature", "city", "humidity"]
}
// 输出:
// {httpRequestRet1} = "25"
// {httpRequestRet2} = "北京"
// {httpRequestRet3} = "60"

HttpRequestHeaderBodyJsonMapAdapter 详解

同时解析响应头和 JSON 响应体。MVEL 表达式中可以访问 headers 和 body 两个变量。

原理（代码第 204-235 行）：

  1. 将响应体解析为 JSON 对象（body）
  2. 将响应头解析为 Map（headers，特殊字符如 - 和空格会被替换为 _）
  3. 对每个 expression 执行 MVEL 表达式，headers 和 body 作为变量传入

示例：同时获取响应头和响应体

// 配置 adapter:
{
  "@type": "type.googleapis.com/HttpRequestHeaderBodyJsonMapAdapter",
  "expressions": ["body.token", "headers.Content_Type"]
}
// 输出:
// {httpRequestRet1} = "abc123"（JSON 中的 token 字段）
// {httpRequestRet2} = "application/json"（响应头 Content-Type）

注意： 响应头中的 - 和空格会被替换为 _，例如 Content-Type 变为 Content_Type。

上下文变量

变量名说明
{httpRequestRet}原始适配器：完整响应体字符串
{httpRequestRet1}JSON 适配器：第 1 个表达式的解析结果
{httpRequestRet2}JSON 适配器：第 2 个表达式的解析结果
{httpRequestRetN}JSON 适配器：第 N 个表达式的解析结果

完整示例

示例 1：GET 请求获取天气（原始响应）

{
  "@type": "type.googleapis.com/HttpRequest",
  "url": "https://api.example.com/weather?city=beijing",
  "method": "GET",
  "adapter": {
    "@type": "type.googleapis.com/HttpRequestRawAdapter"
  }
}
// {httpRequestRet} = 完整的 JSON 响应字符串

示例 2：GET 请求解析 JSON 字段

{
  "@type": "type.googleapis.com/HttpRequest",
  "url": "https://api.example.com/weather?city=beijing",
  "method": "GET",
  "adapter": {
    "@type": "type.googleapis.com/HttpRequestJsonMapAdapter",
    "expressions": ["temperature", "city", "weather"]
  }
}
// {httpRequestRet1} = 温度
// {httpRequestRet2} = 城市名
// {httpRequestRet3} = 天气状况
// 后续动作可以用 {"@type": "type.googleapis.com/ShowToast", "message": "天气: {httpRequestRet1}°C, {httpRequestRet3}"}

示例 3：POST 请求发送 JSON 数据

{
  "@type": "type.googleapis.com/HttpRequest",
  "url": "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=YOUR_KEY",
  "method": "POST",
  "headers": [
    {"key": "Content-Type", "value": "application/json"}
  ],
  "requestBody": {
    "@type": "type.googleapis.com/HttpRequestBodyJson",

    "@type": "type.googleapis.com/HttpRequestJsonMapAdapter",
    "expressions": ["errcode", "errmsg"]
  }
}
// {httpRequestRet1} = 0（成功）
// {httpRequestRet2} = "ok"

示例 4：带 Cookie 的请求

{
  "@type": "type.googleapis.com/HttpRequest",
  "url": "https://example.com/api/userinfo",
  "method": "GET",
  "withCookieJar": true,
  "adapter": {
    "@type": "type.googleapis.com/HttpRequestJsonMapAdapter",
    "expressions": ["name", "email"]
  }
}
// Cookie 会自动保存和发送，适合需要登录的网站

  • 调用天气/新闻/股票等公开 API 获取数据

退出指令是指在触发器触发并且满足条件时，退出当前的指令，结束该指令的所有未完成的动作。

Proto 定义：

{
  "@type": "type.googleapis.com/OpenUrl",
  "url": "示例值",
  "browserPkg": "示例值"
}

自动指令退出 (RuleQuit)

当触发器事件不匹配自动指令的正常触发器时，系统会检查退出逻辑：

正常触发器不匹配 → 检查 quit.isEnabled → 匹配退出触发器 → 检查退出条件 → 取消运行中的任务 → 执行退出动作

退出字段：

字段说明
quit.isEnabled是否启用退出指令
quit.facts退出触发器列表
quit.conditions退出条件列表
quit.condOp退出条件组合方式
quit.actions退出动作列表
quit.evaluatePolicy退出评估策略
| quit.actionAsyncMode

退出评估策略 (Quit_EvaluatePolicy)：

策略说明
Always总是评估退出逻辑
Only_When_Is_Running仅当有运行中的任务时评估
| Once

实际应用场景：
- VPN 应用进入前台时开启 VPN，退出前台时关闭 VPN
- 应用进入前台时播放音乐，退出时暂停

一键指令退出 (DirectActionQuit)

一键指令也支持退出指令，结构与自动指令退出相同。

9. 钩子机制 (Hook)

钩子允许在自动指令/一键指令的生命周期事件中执行额外动作。对应 UI 中的"被启用时"、"被禁用时"、"被删除时"、"被停止时"、"更新时"。

自动指令钩子 (RuleHook)

钩子 i18n 名称 说明
actionsOnEnabled 被启用时 自动指令被启用时执行
actionsOnDisabled 被禁用时 自动指令被禁用时执行
actionsOnDeleted 被删除时 自动指令被删除时执行
actionsOnUpdated 更新时 自动指令被更新时执行
actionsOnStop 被停止时 自动指令停止时执行

示例：自动指令启用时初始化目录

{

  }
}

一键指令钩子 (DirectActionHook)

钩子 说明
actionsOnStart 指令启动时执行
actionsOnStop 指令停止时执行

11. 脚本引擎

11.1 JavaScript (ExecuteJS)

使用 Rhino JavaScript 引擎执行脚本。

线程切换： ExecuteJS 支持通过 context 字段指定执行线程：

上下文 说明
Default 默认协程线程池
IO IO 线程池（适合网络/文件操作）
UI 专用 UI Handler 线程（适合创建浮窗、View 操作）

Proto 定义：

{
  "id": "函数唯一ID",
  "name": "函数名称",
  "returnType": "string",
  "parameters": [
    {"name": "参数名", "defaultValue": "默认值", "isRequired": false, "comments": "说明"}
  ],
  "actions": [
    {"@type": "type.googleapis.com/ShowToast", "message": "{参数名}"}
  ],
  "resultContextDataKey": "返回值写入的上下文变量名"
}

示例：在 UI 线程创建浮窗

{
  "@type": "type.googleapis.com/ExecuteJS",
  "expression": "importPackage(android.view);\nimportPackage(android.widget);\nnew Handler(Looper.getMainLooper()).post(new Runnable({ run: function() { /* UI 操作 */ } }));",
  "context": "CoroutineContext_UI"
}

可用 Java 类（自动导入）：
- java.io.* - 文件操作
- java.net.* - 网络操作
- org.json.* - JSON 操作
- android.* - Android API

返回值： 设置 jsRet 变量

var jsRet = "Hello World";

访问上下文变量：

var pkgName = {pkgName};  // 直接引用
var title = "{title}";    // 字符串引用

访问全局变量：

var val = globalVarOf$变量名;

示例：读取文件

importClass(java.io.File);
importClass(java.io.BufferedReader);
importClass(java.io.FileReader);

var file = new File("/path/to/file");
var reader = new BufferedReader(new FileReader(file));
var line;
var content = "";
while ((line = reader.readLine()) != null) {
    content += line + "\n";
}
reader.close();
var jsRet = content;

14. 常见使用场景

场景 1：应用前台自动开关 VPN

触发器： AppBecomeFg（VPN 应用进入前台）
条件： VPN 未连接
动作： 启动 VPN 服务

退出触发器： AppBecomeBg（VPN 应用进入后台）
退出条件： VPN 已连接，且没有其他 VPN 应用在前台
退出动作： 停止 VPN 服务

场景 2：通知过滤

触发器： NotificationPosted（通知发布）
条件： 通知来自指定应用
动作：
1. 如果是训练模式 → 显示通知，带"垃圾"/"正常"按钮
2. 如果是运行模式 → 执行 JS 脚本判断是否垃圾通知
3. 如果是垃圾通知 → 移除通知并记录

场景 3：蓝牙/WiFi 自动切换

触发器： BTConnectedTo（连接到指定蓝牙设备）
条件： 无
动作： 连接到指定 WiFi，显示 Toast

场景 4：充电控制

触发器： ChargerPlug（插入充电器）
条件： 电量 >= 80%
动作： 停止充电（通过 Shell 命令）

场景 5：剪贴板搜索

一键指令动作：
1. ShellCommand - 获取剪贴板文件路径
2. ShowTextFieldDialog - 输入搜索关键词
3. ExecuteJS - 搜索剪贴板内容并显示浮窗

场景 6：数据备份到云端

一键指令动作：
1. CreateLocalVar - 初始化变量
2. WriteLocalVar - 写入配置
3. ShellCommand - 执行 curl 上传
4. HttpRequest - 企业微信推送通知

15. 调试与排错

查看执行记录

ShortX 记录了所有触发器发布、条件评估、动作执行的结果。

查看方式：
- 在自动指令详情页查看"执行记录"
- 查看条件评估结果（成功/失败）
- 查看动作执行结果（成功/失败/错误信息）

常见问题

自动指令不触发：
1. 检查自动指令是否启用
2. 检查触发器配置是否正确
3. 检查是否有 FactPublishInterceptor 过滤
4. 确认 SystemReady 已发布（开机后需要等待系统就绪）

动作执行失败：
1. 检查 actionOnError 设置（Continue/Break）
2. 查看执行记录中的错误信息
3. 确认所需权限已授予
4. 检查 Shell 命令是否需要 Root

变量引用失败：
1. 确认变量名拼写正确
2. 确认使用了正确的引用语法（globalVarOf$/localVarOf$/{}）
3. 确认变量已创建

脚本执行错误：
1. JavaScript 错误会记录在执行日志中
2. 检查脚本语法
3. 确认使用了正确的返回变量名（jsRet/mvelRet）

调试技巧

  1. 使用 ShowToast 输出调试信息
{
  "@type": "type.googleapis.com/ShowToast",
  "message": "调试: {变量名}"
}
  1. 使用 ShowAlertDialog 显示详细信息
{
  "@type": "type.googleapis.com/ShowAlertDialog",
  "title": "调试信息",
  "message": "当前包名: {pkgName}"
}
  1. 使用 ShellCommand 输出到日志
{
  "@type": "type.googleapis.com/ShellCommand",
  "command": "log -t ShortX '调试信息: $VARIABLE'"
}
  1. 使用 WriteGlobalVar 记录状态
{
  "@type": "type.googleapis.com/WriteGlobalVar",
  "varName": "调试日志",
  "valueAsString": "执行时间: {serialNumber}",
  "op": "WriteGlobalVarOp_AppendToLast"
}

附录 A：ActionOnError 说明

每个动作都有 actionOnError 字段，控制出错时的行为：

值 说明
Continue 继续执行后续动作
Break 停止执行后续动作

附录 B：ConflictStrategy 说明

当自动指令的触发器连续触发时，冲突策略决定如何处理：

策略 说明
ExecuteBoth 同时执行新旧任务
ReplaceOld 用新任务替换旧任务
SkipNew 跳过新任务

附录 C：AsyncMode 说明

指令级别的异步模式：

模式 说明
Async 异步执行，不等待完成
Sync 同步执行，使用全局锁
Sync_InRule 同步执行，使用指令级锁
