边缘手势子手势需求文档

一、需求目标

为现有边缘手势触发器新增“子手势”能力。

当用户先完成一个主边缘手势后，ShortX 需要在同一次触摸流中继续识别后续的子手势步骤，并且只有整段手势序列全部匹配成功时，才触发最终规则。
主手势成功后，在用户松手之前，不应因为等待时间过长而自动取消对子手势的等待。

二、需求范围

本期需求包含：

1. 为 `EdgeGesture` 增加主手势与子手势的建模能力。
2. 在规则触发器配置页中支持为边缘手势配置一个子手势。
3. patch-systemui 侧在现有边缘手势检测基础上增加序列识别能力。
4. 支持以下子手势类型：
   1. 左滑。
   2. 右滑。
   3. 上滑。
   4. 下滑。
   5. 悬停。
5. 继续复用现有边缘手势的热区、拦截模式、自定义矩形、前台应用约束、手势提示等能力。

本期明确不包含：

1. 不新增多指子手势。
2. 不新增分支型手势树。
3. 不把多个普通 fact 组合成顺序触发来替代该能力。
4. 不支持鼠标或手写笔语义下的系统 hover 事件。
5. 不开放用户可配置的子手势等待时长、悬停阈值和提示器样式。

三、核心业务定义

边缘手势子手势定义如下：

1. 用户先从某个边缘热区触发一个主手势。
2. 主手势成功后，系统进入后续识别等待状态。
3. 只要同一 pointer 仍保持按下，系统就持续等待并识别后续动作。
4. 如果后续动作匹配用户配置的子手势，则整段序列成功。
5. 如果后续动作方向错误、抬手或中断，则整段序列失败。
6. 只有整段序列成功，才发布最终 runtime fact 并触发规则。

补充说明：

1. “无等待超时”只适用于主手势成功后到子手势触发前的等待阶段。
2. `Hover` 子手势自身仍然需要满足固定停留时长，但只在用户松手时才结算是否成功。
3. 系统不应在等待阶段自动回退并触发同一条规则的主手势结果。

四、悬停定义

本需求中的“悬停”不是 Android 原生 hover 事件。

其定义为：

1. 主手势完成后，手指保持按下。
2. 在一个较小半径范围内没有明显移动。
3. 持续一段固定时长后，继续保持按下但不立即触发。
4. 只有当用户松手时，系统才根据停留时长与位移范围判定是否悬停成功。

五、等待态提示器

当主手势成功、系统进入等待子手势阶段后，需要向用户展示一个运行时指示器。

其要求如下：

1. 指示器在主手势成功后立即出现。
2. 指示器持续显示，直到子手势成功、序列失败或用户松手。
3. 指示器至少需要表达“系统正在等待子手势”这一状态。
4. 指示器应尽量提示当前期望的子手势方向或类型。
5. 指示器应锚定在当前手势上下文附近，避免让用户丢失操作目标。
6. 指示器不要求用户可配置视觉样式，但需要保证可读、轻量、不中断手势操作。

六、用户功能需求

（一）规则编辑器配置

1. 用户在创建或编辑 `EdgeGesture` 触发器时，可以继续配置主手势。
2. 用户可以为该边缘手势额外添加一个子手势。
3. 子手势可以选择：
   1. 左滑。
   2. 右滑。
   3. 上滑。
   4. 下滑。
   5. 悬停。
4. 用户不配置子手势时，当前边缘手势仍按原有单段模式工作。
5. 再次进入已有规则时，主手势和子手势都需要正确回填。

（二）展示与摘要

1. 当未配置子手势时，摘要保持现有一段式表达。
2. 当配置了子手势时，摘要应体现完整顺序。
3. 例如可表达为：
   1. 底部中间 -> 上滑。
   2. 底部中间 -> 上滑 -> 悬停。

（三）运行时提示

1. 当主手势成功且配置了子手势时，用户需要看到进入等待子手势阶段的提示。
2. 如果子手势是方向型步骤，提示器应尽量体现对应方向。
3. 如果子手势是 `Hover`，提示器应尽量体现“保持按住等待”的状态。

七、运行时需求

1. patch-systemui 仍然先使用现有边缘热区命中逻辑确定候选区域。
2. 当候选规则是单段边缘手势时，保持现有即时识别和触发逻辑。
3. 当候选规则包含子手势时，不应在主手势成功后立即触发规则。
4. 系统需要进入后续步骤识别状态机，直到：
   1. 所有步骤成功，触发规则。
   2. 任一步骤失败，取消序列。
5. 整个序列应只在同一次触摸流内完成。
6. 在主手势成功后到子手势触发前，不应设置自动超时取消。
7. 如果中途抬手，则视为序列失败。
8. 进入等待子手势阶段后，应同步展示运行时提示器。

八、与现有边缘手势的关系

1. 子手势能力是现有 `EdgeGesture` 的扩展，而不是新 fact 类型。
2. 现有边缘手势配置项仍然有效：
   1. 边缘位置。
   2. 自定义矩形热区。
   3. 拦截模式。
   4. 前台应用约束。
   5. 手势提示器。
3. 没有子手势的边缘手势规则，必须保持现有行为不变。

九、与拦截模式的关系

1. 拦截模式仍然只由主边缘热区决定。
2. 命中主热区后，如果该规则开启拦截模式，则可以像现有边缘手势一样尽早偷取输入流。
3. 子手势本身不引入新的独立拦截热区。
4. 后续子手势识别在已取得的同一触摸流上完成。

十、兼容性要求

1. 历史规则如果只有原始 `gesture` 字段，应继续按单段边缘手势处理。
2. 新增子手势字段后，旧规则在 UI 中应正确映射为：
   1. 主手势为旧值。
   2. 子手势为空。
3. 未配置子手势的新规则，也应与当前逻辑完全一致。

十一、异常与边界处理

1. 主手势成功后长时间保持按下但未触发子手势：继续等待，不自动失败，也不触发该规则。
2. 主手势成功但后续方向错误：整段失败，不触发规则。
3. 主手势成功但中途抬手：整段失败，不触发规则。
4. 悬停阶段位移超过允许半径：整段失败，不触发规则。
5. 非序列规则不应受到序列检测逻辑干扰。
6. 等待态提示器在成功、失败、松手后必须及时消失。

十二、验收标准

1. 用户可以在边缘手势配置页中添加一个子手势。
2. 保存后再次编辑，子手势配置能够正确回填。
3. 不配置子手势时，现有边缘手势行为不回归。
4. 配置方向型子手势后，只有主手势和子手势都成功时才触发规则。
5. 配置悬停子手势后，只有主手势成功且后续按住停留满足条件，并在松手时结算通过后才触发规则。
6. 主手势成功后只要不松手，即使等待较长时间，系统仍保持对子手势的等待。
7. 主手势后如果抬手或方向错误，不会误触发规则。
8. 等待子手势期间会显示明确的运行时提示器，并在成功、失败、松手后正确消失。
9. 拦截模式、自定义热区、前台应用约束等现有能力与子手势能力可同时工作。
