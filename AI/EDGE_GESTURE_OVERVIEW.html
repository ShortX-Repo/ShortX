ShortX Gesture Runtime

边缘手势整套检测与处理逻辑总览

这份文档只基于当前仓库里的真实代码链路整理，覆盖主手势、子手势、预制区域、自定义区域、绝对区域、提示反馈、连续动作和规则触发。 看完它，应该能直接回答三个问题：用户到底配置了什么、运行时如何识别、最终怎样回到规则引擎触发动作。

入口方式 InputMonitor 路径进到 GestureService，再交给 ShortXGestureMain
区域模型 自定义矩形 + 预制边缘；预制边缘同时产出相对/绝对两套命中结果
主手势 单击 / 双击 / 长按 / 四方向滑动 / 连续动作入口
子手势 Hover 与方向步骤串联，同一根手指连续识别
一句话心智模型 先用区域解析器把按下点变成一组 DetectedArea，再由 EdgeGestureEngine 决定这是普通手势、连续动作还是子手势序列，最后通过 GestureBridgeImpl 把命中的事实重新发回规则系统。
Part 1

这套系统到底支持什么

先看功能边界，再看实现细节。

触发区域

  • 预制边缘：Left / Right / Top / Bottom 及细分 Top/Center/Bottom、Left/Center/Right。
  • 自定义区域：用户直接配置一个屏幕矩形，命中时不再走预制边缘匹配。
  • 父区域回退：例如命中 RightCenter 时，规则仍可配置 RightAll。

主手势类型

  • SingleTap / DoubleTap / LongTap。
  • SwipeFromLeft / Right / Top / Bottom。
  • 连续动作入口：亮度、音量、指针模式等。

扩展语义

  • 绝对区域：预制边缘在横屏下仍按竖屏语义解释。
  • 子手势：在主手势命中后继续识别 Hover / 二段方向。
  • 反馈：提示线索与触觉反馈按规则开关分别控制。

Part 3

端到端运行时总流程

这是你排查问题时最重要的一张图。

系统输入层

  • InputMonitor 收到 MotionEvent
  • GestureService.filterInput()
  • ShortXGestureMain.filterMotionEvent()

区域检测层

  • EdgeRegionResolver.detectAreas()
  • 先扫 customRect
  • 再产出 Relative + Absolute 预制边缘

主手势判定层

  • EdgeGestureEngine 接管状态机
  • LongPress / DoubleTap 定时器
  • 滑动方向解析与阈值判定

反馈与二段识别

  • HintDetector 实时提示
  • SequenceDetector 继续跟踪子手势
  • 连续动作处理器接管 move/up

规则触发层

  • GestureBridgeImpl 匹配规则
  • fireEdgeGesture / fireEdgeGestureSequence
  • 回到 ShortX 规则引擎执行动作
A

ShortXGestureMain 是现行 runtime 装配入口

它先尝试 CornerSwipeToCenterDetector，再把剩余事件交给 EdgeGestureEngine。也就是说，角落滑向中心先于边缘手势判定。

B

GestureService.filterInput() 是进入这套系统的服务层入口

当前仓库里并不是直接在 Engine 接原始输入，而是由 GestureService 做桥接。这里也复用了录制逻辑。

C

Engine 一旦确认接管，会缓存 DOWN，并在失败时 replay

这也是它为什么维护 cachedDownEvent、gestureCaptured、executionStarted 等状态字段。

Part 4

区域检测逻辑：预制和自定义到底怎么并存

这部分是“为什么同一个 down 点会产生多个候选区域”的关键。

自定义区域

  • 先从所有启用规则里抽出带 customRect 的规则。
  • 按矩形去重，按 left/top/right/bottom 排序，保证检测顺序稳定。
  • 命中后生成 DetectedArea.CustomRect(rect)。
  • 自定义区域规则不会再参与预制边缘模式匹配。

预制边缘

  • 同一个 down 点会同时解析两套结果：RelativeToDisplay 和 AbsolutePortrait。
  • Relative 模式随当前屏幕方向变化。
  • Absolute 模式先把当前触点逆变换回竖屏坐标，再做边缘命中。
  • 规则匹配时根据 useAbsoluteArea 只吃自己那一套坐标语义。
DetectedArea

CustomRect(rect)

对 customRect 规则做强匹配，不参与 edge + parent fallback。

DetectedArea

PredefinedEdge(edge, RelativeToDisplay)

横屏时跟着当前显示方向转，适合“看屏幕方向做手势”。

DetectedArea

PredefinedEdge(edge, AbsolutePortrait)

横屏仍然按竖屏配置解释，适合“记忆固定方位”。

Fallback

ParentEdge

命中 RightCenter 时，如果规则配的是 RightAll，也能继续命中。

Part 5

主手势检测状态机

单击、双击、长按、四方向滑动都在这一个 engine 里统一收口。

1

ACTION_DOWN

  • 记录 downX/downY，同时算一份绝对竖屏坐标 downAbsoluteX/downAbsoluteY。
  • 调用 detectAreas() 得到 hitAreas。
  • 缓存 DOWN 事件，启动长按计时器。
  • 如果一个区域都没命中，直接退出，不进入手势系统。
2

ACTION_MOVE：先识别方向，再决定是否真正执行

  • 方向不是一份，而是两份：相对屏幕方向和绝对竖屏方向。
  • Engine 把两套方向都转成 Gesture，形成 recognizedSwipeGestures。
  • 只有走到 swipeDistanceThreshold 之后，才进入真正的动作执行或子手势模式。
3

执行分流

  • 如果命中连续动作绑定：创建 ContinuousActionHandler 接管 onMove/onFinish/onCancel。
  • 如果命中普通规则：直接 fireEdgeGestureEvent。
  • 如果命中带 childSteps 的规则：sequenceDetector.startTracking() 进入二段识别。
4

ACTION_UP / CANCEL

  • 未进入 executionStarted 时，会继续走单击 / 双击 / 长按收尾逻辑。
  • 判定失败则 replay 缓存的 DOWN。
  • 成功则消费缓存事件，重置状态。
为什么要同时保留 relative 和 absolute 两套方向？
因为同一条物理滑动，在横屏下既可能对应“当前屏幕里的向左”，也可能对应“竖屏语义里的向上”。只有两套都算出来，规则层才能让不同手势各取所需。
Part 6

子手势检测逻辑

主手势成功后，同一根手指如何继续识别 Hover / 二段方向。

序列跟踪怎么启动

  • 只有带 childSteps 的规则才会进入 EdgeGestureSequenceDetector。
  • startTracking() 收到 primaryGesture、down 坐标、当前 anchor 和候选规则列表。
  • 候选规则不是一个，而是一组，后续每命中一步都会收缩一次。

当前步骤的两类形态

  • Hover：看停留时间和偏移半径。
  • Directional Step：看方向点积、最小距离、回退容忍度。
  • 引擎内部用 StepPhase 区分 Undecided / HoverTracking / LockedDirection。
阶段 判断依据 绝对区域如何影响
候选生成 当前 stepIndex 下，哪些规则还有下一步 不影响候选列表本身，只影响后续方向计算坐标系
Hover 匹配 anchor 半径内停留到 hoverDurationMs Hover 用的是距离窗口，不依赖旋转语义
方向步骤匹配 方向点积、最短距离、锁方向、回退容忍 按规则逐条选坐标：relative 用屏幕坐标，absolute 用竖屏映射坐标
最终触发 所有 childSteps 全部完成 通过 GestureBridgeImpl.fireEdgeGestureSequence() 回发 EdgeGesture 事实
Part 7

提示反馈和触觉反馈怎么插入

提示不是单独的一套判定系统，而是贴着主手势和子手势实时旁路运行。

主手势提示

  • EdgeGestureHintDetector 在 ACTION_DOWN 收集当前 down 点的所有候选区域。
  • ACTION_MOVE 时同时计算相对 delta 和绝对 delta。
  • 如果某条规则启用了 useAbsoluteArea，就用绝对 delta 来决定箭头方向与 ready 状态。

子手势提示

  • SequenceDetector 通过 EdgeGestureSequenceHintSink 把当前步骤的 progress、ready、hint/haptic 开关吐给 UI 层。
  • Hover 和方向步骤使用不同的进度模型。
  • 进入 sequence 后，主手势提示会取消，避免两套反馈打架。
Part 8

规则匹配与动作回发

真正触发动作的不是 engine 本身，而是 bridge 负责把识别结果重新变回事实。

I

GestureActionResolver 负责普通规则命中

它只关心两件事：当前 areas 列表里有没有和规则一致的区域，以及当前 gesture 是否匹配。自定义区域和预制边缘用不同分支处理。

II

GestureBridgeImpl 负责三类输出

  • 普通手势：handleEdgeGestureEvent()
  • 子手势规则候选：findMatchingEdgeGestureSequences()
  • 完整子手势成功：fireEdgeGestureSequence()
III

最终还是回到 EdgeGesture 事实

不论是普通手势还是子手势序列，最后都重新构造一个 EdgeGesture proto，再由 shortx.fireEdgeGesture / fireEdgeGestureSequence 发回规则系统。所以 runtime detector 不直接执行业务动作，它只负责识别并回发事实。
