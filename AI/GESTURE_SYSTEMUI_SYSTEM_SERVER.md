核心区别不在你这段业务判断，而在“代码挂在哪一层”。

原来 server 里的 filterInput，本质上是挂在输入分发链的前面，事件还没正式发给目标窗口时，你就已经拿到它了。像 GestureService.kt:95 这种方案，决定权在你手里：放行、拦截、延后、甚至失败后自己回放，都是因为原始事件流从入口起就归你控制。换句话说，旧方案是“先判定，再决定要不要让别人看到”。

InputMonitor 不是这个位置。你现在这条链在 InputMonitorInstaller.kt:21 里通过 monitor receiver 拿事件，而 receiver 的 consumed 语义只是结束你这个 receiver 对事件的处理，不等价于撤销系统已经做出的分发决定。pilferPointers() 也不是“把这次手势从头拿走”，它更像“从现在开始，后续这串 pointer 归我”。所以它天然只能抢后半段，抢不到前半段。也正因为如此，旧方案里“失败就回放”只要回放你扣下来的原始事件即可；新方案里如果前几帧已经到过目标窗口，或者你只缓存了一个 DOWN，那你就没法还原出一条完整、无副作用的手势流。

所以这两种大方案的本质差异是：

旧方案是入口拦截。
你拥有原始事件的一次分发权，所以可以做真正的 veto 和完整 replay。

新方案是旁路观察加中途接管。
你先看到的是镜像流，等你决定 pilfer 时，往往已经晚于首帧分发，只能接管后续事件，不能天然复刻“从 ACTION_DOWN 开始完全托管”。

旧方案更像事务。
要么整条事件都交给 ShortX，要么整条都交给目标应用。

新方案更像热切换。
前半段可能已经给了目标应用，后半段才切到 ShortX，这就会出现你现在看到的“候选阶段抢早了会断流，抢晚了又不是完整拦截”的矛盾。

这也是为什么你现在这套 monitor 逻辑即使分支判断没反，效果仍然和 server filter 不一样。不是业务 if 写错了，而是底层时序和所有权已经变了。

如果你要的是“尽量接近旧行为”，更现实的方向通常有两个：

接受 InputMonitor 的边界，改成“确认触发后才 pilfer”，不追求失败时无损回放。
自己缓存被接管后的整段事件序列，失败时重放整段，而不是只重放一个 DOWN。这也只能逼近旧方案，不能完全等价。
